# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Maison": a household PWA for two people (loyalty cards, weekly meals, recipes, shopping list + product catalogue, restaurants (tried / to try, map, visits), shared expenses, private journals, manual budget of monthly/yearly charges). Everything user-facing, all code comments, API error messages and commit messages are in **French**: keep it that way.

## Commands

No test suite exists. Verify changes by type-checking/building.

```sh
# backend (Fastify API on :3000, reads backend/.env: DATABASE_URL, JWT_SECRET, ADMIN_* for the first start only)
cd backend && npm i && npx prisma migrate dev && npm run seed && npm run dev
npm run build                          # tsc → dist/
npx prisma migrate dev --name <name>   # after editing prisma/schema.prisma

# frontend (Vite on :5173, proxies /api → localhost:3000)
cd frontend && npm i && npm run dev
npm run build    # tsc -b && vite build
npm run lint     # eslint
```

Deployment: `docker compose up -d --build` (single image, port 1000, behind cloudflared). The container runs `prisma migrate deploy`, then the seed, then the server. SQLite DB and uploaded photos live in the `data` volume (`DATA_DIR=/data`).

## Architecture

Two independent npm packages, `backend/` and `frontend/`, combined in one Docker image: in production Fastify serves the built frontend from `PUBLIC_DIR` with an SPA fallback to `index.html` (anything not under `/api`).

### Backend (`backend/src`)
- Fastify 5 + Prisma 6 on SQLite, ESM (imports use `.js` extensions), Zod for all request validation. A `ZodError` thrown from a handler is turned into a 400 by the global error handler in `server.ts`; other errors with `statusCode < 500` return their message.
- `server.ts` mounts everything under `/api`; `/api/auth` is public, every other route plugin is registered inside a scope with the `requireAuth` preHandler. New route modules go in `routes/` and get registered there.
- Auth: JWT in an httpOnly `session` cookie (30 days). `req.user` is `{ id, householdId }`.
- **Familles et pages activées** (`modules.ts`, `routes/admin.ts`, `pages/Admin.tsx`): plusieurs `Household` indépendants dans la même base. `Household.features` (CSV) liste les pages activées pour la famille (`MODULES` : cartes, repas, recettes, courses, restos, depenses, infos, budget). **Espace privé** : `journal`, `calories` et `media` ne sont plus des pages de famille mais `PRIVATE_MODULES`, réservés à `User.isAdmin` (ajoutés à `req.access.features`, exposés à part dans `privateFeatures`) ; le front les range sous `/prive` (choix « Famille / Mon espace » en haut de l'accueil, barre de menu et titre propres, `usePrivateTabs`/`isPrivatePath` dans `lib/tabs.ts`). `requireAuth` charge la personne et ses droits (`req.access`) à chaque appel ; le hook `requireModule` refuse (403) toute route dont le segment n'est pas autorisé par `ROUTE_MODULES` (une page peut en autoriser d'autres : les recettes servent au planning et aux calories, les courses aux recettes) et protège `/api/admin` (`User.isAdmin`). L'administrateur crée une famille et ses comptes depuis `/admin` avec un mot de passe provisoire (`mustChangePassword` : tout est refusé hors `/auth` tant qu'il n'est pas changé ; le front affiche `FirstLogin`). Le front masque les pages (`allowedTabs`, `Gate` dans `App.tsx`) mais seul le serveur fait foi. Une nouvelle page doit être ajoutée à `MODULES`, à `ROUTE_MODULES` et à `tabs`.
- **Sessions** : le JWT porte `sv` = `User.sessionVersion` ; un changement ou une réinitialisation de mot de passe l'incrémente, ce qui invalide les anciens cookies. Mot de passe : 10 caractères minimum.
- **En-têtes de sécurité** : CSP, nosniff, etc. posés par le hook `onSend` de `server.ts`. Toute nouvelle ressource externe (police, tuiles, image distante) doit être ajoutée à la CSP, sinon le navigateur la bloque. Le conteneur tourne sous l'utilisateur `node` (voir `CMD` du Dockerfile).
- **Data scoping**: every model hangs off a `Household`. Queries must always filter by `req.user.householdId`. Models also carry `createdById` and `ownerId`: `ownerId: null` means shared within the household; a set `ownerId` means private to that user (used by journals, reserved for later elsewhere).
- Conventions in the schema: dates are `YYYY-MM-DD` strings, enums are plain strings (comments list values), money is integer cents. A reimbursement is an `Expense` with `isReimbursement` paid by the debtor and shared to the creditor. `Product.nameKey` is a normalized name (lowercase, no accents) used for matching shopping items to products.
- Images (cards, products): multipart with a single optional `image` field, handled by `uploads.ts` (`readMultipart` / `saveImage` / `removeImage` / `sendImage`), stored in `DATA_DIR/uploads`, served via `GET /api/{cards|products}/:id/image`.
- **Budget** (`routes/budget.ts`, `frontend/src/lib/budget.ts`, `pages/Budget.tsx`): manual entry, no bank connection. A `BudgetItem` is a charge or income (`kind` EXPENSE | INCOME) that recurs `MONTHLY` or `YEARLY` (`dueDay`, plus `dueMonth` for yearly); amounts are positive integer cents, the sign comes from `kind`. Same visibility model as `HouseInfo`: `ownerId` null = shared, set = private (new items default to private). All totals (monthly equivalent = yearly ÷ 12, "reste par mois", 12-month calendar) are computed on the frontend from `GET /api/budget`. Category ids are duplicated in `routes/budget.ts` and `frontend/src/lib/budget.ts`. Budget data is deliberately not persisted offline. **Charge commune** (`ownerId` null, `EXPENSE`) : `paidById` = qui paie, `lastBilledOn` = dernier report ; `syncBudgetExpenses` (`budgetSync.ts`, appelé par `GET /api/budget` et `GET /api/expenses`, pas de tâche planifiée) crée à chaque échéance échue une `Expense` dans le carnet « Vie quotidienne » (créé s'il manque), répartie à parts égales entre les membres. Le report démarre à l'enregistrement, sans rattraper le passé.
- **Calories** (`routes/calories.ts`, `lib/calories.ts`, `pages/Calories.tsx`): suivi strictement personnel (`CalorieEntry.ownerId` toujours renseigné, jamais partagé), une ligne = un repas saisi (`meal` BREAKFAST | LUNCH | DINNER | SNACK, `kcal` entier). `GET /api/calories?from&to` renvoie une plage de jours. L'objectif quotidien est `User.calorieGoal` (via `/auth/preferences`). `Recipe.calories` = kcal par portion (importé depuis `nutrition.calories` du JSON-LD si présent) ; la fiche recette propose « Calories » pour l'ajouter au suivi du jour (`RecipeToCalories`). Scan de produit : `BarcodeScanner` (caméra, `@zxing/browser` chargé à la demande) lit un code-barres, `GET /api/calories/product/:barcode` interroge Open Food Facts côté serveur (kcal pour 100 g) et le formulaire calcule le total d'après les grammes. Pas de catalogue produits, mais **« Mes aliments »** : une `Recipe` avec `ownerId` = moi (privée : `GET /api/recipes` renvoie les recettes partagées + mes aliments, avec `private`), `per100g` = calories données pour 100 g (produit scanné) au lieu de par portion. Gérés dans l'espace privé, page Calories › « 🍲 Mes recettes » (`pages/CalorieFoods.tsx`, fiche sous `/calories/recettes/:id` = `RecipeDetail` ; `/recettes/:id` d'une recette privée y redirige) et absents de la liste Recettes de la famille. Créés par `RecipeForm caloriesOnly` ou par « ⭐ Garder dans mes aliments » dans `CalorieEntryForm` ; `private` n'est lu qu'à la création. Un aliment **composé** (ex. petit-déj pain + fromage + jambon) stocke ses produits dans `ingredients`, une ligne « 40 g Pain · 250 kcal/100 g » (`partsToText`/`textToParts` dans `lib/recipes.ts`, éditeur `FoodParts`, produits scannés ou saisis) et `calories` = total pour 1 portion. `useRecipes(enabled, withPrivate)` masque les privées par défaut (accueil, recherche, planning) : seuls Recettes, la fiche, `RecipeToCalories` et `CalorieEntryForm` passent `withPrivate`. Données non persistées hors ligne.
- **Médias** (`routes/media.ts`, `mediaSources.ts`, `lib/media.ts`, `pages/Media.tsx`): suivi de ce qu'on regarde, joue ou lit. `MediaItem.kind` MOVIE | SERIES | GAME | BOOK, `status` WISHLIST | IN_PROGRESS | DONE, toujours privé (`ownerId` = moi ; les anciennes fiches partagées restent visibles de l'administrateur). Une vraie base par type, interrogée côté serveur (aucune ressource externe côté navigateur, pas de CSP à changer) : films et séries = TMDB (`TMDB_API_KEY`, clé v3 ou jeton v4), jeux = IGDB (`IGDB_CLIENT_ID` + `IGDB_CLIENT_SECRET`, compte Twitch ; jeton d'accès demandé et gardé en mémoire), livres = Open Library (sans clé). Sans clé, la recherche du type répond 503 et la saisie manuelle reste possible. `GET /api/media/search?kind&q` ; à la création le client envoie `source`/`sourceId` et le serveur va chercher résumé, créateur et affiche (téléchargée sur `image.tmdb.org`, `covers.openlibrary.org`, `images.igdb.com` seulement, stockée dans `uploads`). Ajouter un type = une entrée dans `SOURCES` + `KINDS` (`lib/media.ts`). Mention TMDB affichées dans la recherche (obligation de leurs conditions). Page de l'espace privé de l'administrateur. Données non persistées hors ligne.
- **Poids** (`routes/weight.ts`, `garmin.ts`, `lib/weight.ts`, `pages/Weight.tsx`): suivi strictement personnel (`WeightEntry.ownerId` toujours renseigné), une pesée par jour (`@@unique([ownerId, date])`, poids en grammes, `bodyFat` en %). Objectif = `User.weightGoal` (grammes, via `/auth/preferences`). `source` MANUAL | GARMIN : `POST /api/weight/sync` interroge l'API personnelle Garmin Connect côté serveur (`GARMIN_API_KEY`, clé qui expire : jeton d'accès via `personalapitoken-service`, puis `weight-service/weight/range`) et n'écrase jamais une pesée MANUAL ; sans clé, la synchronisation répond 503 et la saisie manuelle reste possible. `muscleGrams` (muscle, Garmin ou saisi) alimente l'analyse de `lib/weight.ts` (`analyse` : variation poids / muscle / gras / reste entre la moyenne des 3 premières et des 3 dernières pesées, verdict prise de qualité, perte propre, etc. ; seuil de bruit 300 g). La synchronisation repart d'un an tant qu'une pesée Garmin n'a pas de muscle. Page de l'espace privé de l'administrateur. Données non persistées hors ligne.
- **Santé** (`routes/garmin.ts`, `garmin.ts`, `lib/garmin.ts`, `pages/Health.tsx`, `components/health/`): lecture seule de l'API personnelle Garmin Connect (`GARMIN_API_KEY`, la même que pour le poids), **rien n'est stocké** : le serveur reformate les réponses en objets simples (`GET /api/garmin/overview|activities|forme|weight-goal`) et les garde 3 minutes en mémoire ; le jeton d'accès est gardé jusqu'à son expiration, un 401 déclenche un seul nouvel essai. Sans clé, tout répond 503. Trois onglets : Résumé (pas via `v2/dailysummaries`, minutes intenses sur 7 jours glissants, batterie corporelle), Sport (100 dernières sorties, filtre par type, fiche détaillée, zone cardiaque d'après `heartRateZones`), Forme (âge de forme, zones cardiaques, sommeil seulement s'il est mesuré). La montre n'est portée que pour le sport : la FC de repos de Garmin est donc faussée et volontairement ignorée ; sommeil, stress, HRV et hydratation n'apparaissent que s'ils existent. Dates « du jour » calculées en `Europe/Paris` côté serveur. Page chargée à la demande (`React.lazy` dans `App.tsx`) pour ne pas grossir le bundle principal. L'objectif de poids Garmin peut être repris dans la page Poids. Page de l'espace privé de l'administrateur.
- **Sport** (tableau de bord ; `routes/training.ts`, `scripts/garmin/`, `lib/training.ts`, `pages/Sport.tsx`, `components/training/Charts.tsx`): page de l'espace privé de l'administrateur (module `sport`, route `/sport`, sélecteur de période 4 sem.–1 an, indicateurs comparés à la période précédente, calendrier de régularité, zones cardiaques, allure) sur l'historique Garmin, **récupéré sur l'ordinateur et non par le serveur** : `scripts/garmin/refresh.sh` (ou `npm run garmin:refresh`, à la racine) lance `pull.mjs` dans Docker (Node 24, sans dépendance, lit `GARMIN_API_KEY` dans `.env`), qui range le brut en JSON dans `garmin-data/` (ignoré par git et par `.dockerignore`) et écrit `summary.json` via `summarize.mjs` (semaines lundi→dimanche, séries quotidiennes, records, tout en km). Relancer ne récupère que le nouveau (`--full` = tout l'historique, `--days=N`). Garmin renvoie une erreur 500 au-delà de ~256 Ko : plages de 60 jours (jours), 30 (nuits), pages de 20 sorties, plage coupée en deux sur un 500. Le conteneur monte `./garmin-data` en lecture seule (`GARMIN_DATA_DIR=/garmin-data`) et `GET /api/training` renvoie `summary.json` (`{ empty: true }` s'il n'existe pas). Objectif réglable dans `garmin-data/config.json` (`runsPerWeek`, `raceDate`, `raceName`). Sections VFC, sommeil, FC au repos affichées seulement si la montre les mesure. Page chargée à la demande (`React.lazy`).
- **Temps réel** (`live.ts`): `GET /api/events` is a Server-Sent Events stream (in-memory hub per household, `: ping` every 25 s for cloudflared). An `onResponse` hook on the `/api` scope (`invalidateOnWrite`) broadcasts the TanStack Query keys to refresh after every successful non-GET, according to the `INVALIDATIONS` URL-prefix map (private data — journals, budget, preferences — only to the same user's devices). New routes whose data other devices show must get an entry there. Only keys are sent, never data.
- **Pages de l'accueil vs barre de menu**: `User.hiddenTabs` masque des pages de la barre, `User.hiddenHome` (copié de `hiddenTabs` à la migration) masque des tuiles de l'accueil ; les deux sont indépendants, réglés dans `Profile.tsx` (`PageList`), et la recherche globale couvre l'union. Une session gardée hors ligne sans `hiddenHome` retombe sur `hiddenTabs` (`useHomeTabs`). Ordre des pages : `User.menuOrder` (CSV, commun à la barre et à l'accueil, flèches ▲▼ dans `PageList`) appliqué par `orderTabs` dans `lib/tabs.ts` (pages inconnues de l'ordre = à la fin). Tuiles sur 2 colonnes : `User.homeWide` (défaut `/repas`). Les tuiles vivent dans `components/home/` (chacune charge ses données ; `Tile` = lien en fond + contenu qui laisse passer les clics, sauf `Action` pour les boutons rapides ; ne jamais mettre un modal dans une tuile : overflow/transform). La barre défile au-delà de 7 pages.
- **Notifications push** (`push.ts`, `routes/push.ts`): Web Push via `web-push`; VAPID keys from `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` or generated once into `DATA_DIR/vapid.json`. `sendPush` skips users who muted the type (`User.mutedNotifications`, CSV: SHOPPING, EXPENSES; unknown legacy values are filtered out) or who are live (an open SSE connection = app on screen), and drops subscriptions answering 404/410. Only two triggers, on purpose, both sent immediately with high urgency: shopping adds (one push per add, the text recaps the same author's adds of the last 2 min and replaces the previous one via the tag) and new expenses. There are no scheduled jobs.
- **Import de recette** (`recipeImport.ts`, `POST /api/recipes/import`): fetches a page server-side, reads the schema.org `Recipe` JSON-LD and returns pre-filled fields (+ photo as data URL) without saving; the frontend shows them in `RecipeForm` via `draft`. Only public addresses are fetched (redirects re-checked).
- `seed.ts` only bootstraps: while no admin exists it creates (or promotes) the account from `ADMIN_EMAIL`/`ADMIN_NAME`/`ADMIN_PASSWORD` (`USER1_*` still read for old `.env` files); once an admin exists the env is ignored and accounts are managed from `/admin`.

### Frontend (`frontend/src`)
- React 19 + React Router 7 + TanStack Query 5 + Tailwind 3 (custom pastel palette and `ink`/`cream` colors in `tailwind.config.js`), PWA via `vite-plugin-pwa`.
- `lib/api.ts` holds the `api()` fetch wrapper (throws `ApiError` with the server's `error` message) and **all shared API types**; keep them in sync with the backend responses by hand.
- Auth state is the `["me"]` query (`lib/auth.ts`); `null` shows `Login`. Any 401 invalidates `["me"]` (global handler in `main.tsx`).
- **Offline**: the query cache is persisted to localStorage, but only the keys listed in `OFFLINE_KEYS` in `main.tsx` (`me`, `shopping`, `cards`, `infos`); `gcTime` is `Infinity` on purpose (see comment there). `lib/offline.ts` warms these queries and preloads their images on startup; the service worker caches `/api/(cards|products)/:id/image` (in `vite.config.ts`). When adding a field to `User` or to persisted data, handle older cached objects lacking it (cf. `hiddenTabs ?? []` in `lib/tabs.ts`).
- **Temps réel / push**: `lib/live.ts` (`useLiveUpdates`, mounted in `Layout`) keeps an `EventSource` open only while the page is visible and invalidates the received keys (all queries after a reconnect); there is no polling. The service worker is generated by workbox and loads `public/push-sw.js` (push display and notification click) through `workbox.importScripts`. `lib/push.ts` handles the per-device subscription; settings are in `Profile.tsx`.
- Navigation: `lib/tabs.ts` defines the menu tabs; users can hide tabs and the nav bar (preferences stored on `User`, updated optimistically via `useUpdatePreferences`). Routes are in `App.tsx`; pages under `Layout` get the shell, `CardDetail` is full-screen.
